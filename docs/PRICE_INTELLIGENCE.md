# 價格快照與可信度設計

## 目的

避免把同一次搜尋最便宜的一張票，拿去與同次搜尋其他較貴的票平均比較，然後宣稱發生歷史降價。也避免將人工預設價格當成市場歷史證據。

## 計算單位

`flight_records` 保留原始報價供稽核。`search_snapshots` 則每次成功搜尋只存一筆最低價，以及查詢雜湊、來源、幣別、旅客數、艙等、日期、直飛條件、offer 數量與觀測時間。

查詢雜湊包括出發／抵達機場、出發／回程日期、來源、幣別、直飛條件、成人數與艙等。現在的 adapter 固定 1 位成人、經濟艙、TWD、不保證行李，擴充新條件時必須同步更改搜尋、snapshot 與 query key，不能只修改畫面。

比的是**相同查詢條件下的最低報價**，不保證每次是相同航空公司、航班或票種。缺乏 fare basis、行李及可售驗證時，不得稱為相同票種的精確跌價追蹤。

## 基準與抽樣偏差

1. 在查價開始時決定比較截止時間；本次與未來觀測不進入基準。
2. 同一查詢同一天的最低價快照取中位數。
3. 對不同觀測日的中位數等權取平均。
4. 分別報告近 7/30/90 日窗口的平均、觀測日數與涵蓋日期跨度。

例如過去五個不同觀測日的基準都是 8,000 元，新搜尋出現 5,500、7,500、9,000、12,000、15,000 元：新增的快照只有 5,500 元，降幅為 `(8000-5500)/8000 = 31.25%`（顯示時以 Python `round` 保留一位小數，本例為31.2%）。不會以同批 offer 均價 9,800 元產生約 44% 的假歷史跌價。

近30日不足五個觀測日：`sufficient_history=false`，折扣分歸零，不建立歷史降價優惠。五日是本專案保守的產品門檻，不是經科學驗證的統計顯著性保證。長窗口標記還要求近90日中至少60個不同觀測日且首末觀測日期跨度覆蓋90個日曆日。

不同出發日期不共用優惠判斷基準；`route_stats` 只是路線摘要，不能當成任意日期的季節調整基準。

## 評分

| 項目 | 最高分 | 證據要求 |
|---|---:|---|
| 絕對價格區間 | 25 | 正的 TWD 報價；區間是排序偏好，非市場證據 |
| 同查詢歷史降幅 | 40 | 至少五個不同觀測日；30/90日不重複計分 |
| 本系統觀測低點 | 10 | 有足夠基準，且比先前最低價低 |
| 直飛條件 | 10 | 查詢設定及已取得航段；去回細節仍需確認 |
| 已知時段 | 5 | 起降時間都有值且不是深夜區間 |
| 已設定便利機場 | 5 | 設定檔中的產品偏好，不是客觀旅遊品質 |
| 行李／票種 | 5（保留） | 尚未取得，現階段不給分 |

目前最高95分，不能以品牌推定托運。資料不足時不標示「市場歷史最低」。`90D_LOW` 需符合長窗口覆蓋條件；一般新低僅描述「本系統此前觀測到的最低價」。

## 相容與遷移

新增三張表，不 ALTER 舊資料表：`search_snapshots`、`task_leases`、`radar_migrations`。一次性 `search-snapshots-v1` 遷移保留原始資料與通知歷史，但停用舊算法的 active deals 並清空舊 RouteStats 摘要。後續啟動不重做。

舊資料缺少完整查詢身分與搜尋批次證據，故不自動回填成可靠快照。先停 worker 並備份資料庫再升級；停止全部連線後才能用備份恢復。不要在程式仍寫入時直接覆蓋 SQLite 檔。

既有 `duration_days` 欄位為回程日減出發日，實際較接近夜數。NLP API 的使用者「天數」轉換為日期差來篩選；完整前端／CLI 的天數命名統一仍列入路線圖，以出回日期為準。

## 邊界

搜尋錯誤不寫零元。報價超過六小時從有效列表排除，並非六小時保價。沒有查價結果不表示所有供應商都售罄。多來源、含行李總價、正式報價再確認及實際庫存尚未完成；不能以本版發出「已確認可下單」訊息。
