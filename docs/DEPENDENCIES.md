# Dependency Locks and Reproducible Builds

The repository commits one canonical resolution artifact per runtime so a
clean checkout reproduces the reviewed dependency graph instead of resolving
compatible ranges at install time.

## Artifacts

| Human-edited manifest | Committed resolution artifact | Deterministic install |
| --- | --- | --- |
| `requirements.txt` | `requirements.lock` | `python -m pip install --require-hashes -r requirements.lock` |
| `requirements-dev.txt` | `requirements-dev.lock` | `python -m pip install --require-hashes -r requirements-dev.lock` |
| `cloudflare/package.json` | `cloudflare/package-lock.json` | `cd cloudflare && npm ci` |

`requirements.lock` and `requirements-dev.lock` are generated by
`uv pip compile` (`uv==0.12.15`) with `--generate-hashes --universal
--python-version 3.12`, so every pinned package carries sha256 hashes and the
files are platform independent. `requirements-dev.lock` includes the full
application graph plus test tools (pytest, playwright).

`cloudflare/package-lock.json` is generated by `npm@10.9.4`
(`lockfileVersion: 3`); `npm ci` installs exactly that graph and fails when it
disagrees with `package.json`.

The Dockerfile base image is pinned by manifest-list digest
(`python:3.12-slim@sha256:…`). The lock compilers themselves are pinned by
version — `uv==0.12.15` and `npm@10.9.4` in the regeneration steps — so a
toolchain upgrade is an explicit, reviewed change; they are not hash-pinned.

## Installing

```bash
# Application runtime (also used by the Dockerfile and scheduled jobs)
python -m pip install --require-hashes -r requirements.lock

# Development / test environment
python -m pip install --require-hashes -r requirements-dev.lock
python -m playwright install chromium   # browser binaries for optional browser tests

# Cloudflare worker tooling
cd cloudflare && npm ci
```

## Updating a dependency

1. Edit the manifest only: `requirements.txt`, `requirements-dev.txt`, or
   `cloudflare/package.json`. Keep the existing range style unless the bump
   needs a tighter bound.
2. Regenerate the matching artifacts with the pinned tools:

   ```bash
   python -m pip install uv==0.12.15
   uv pip compile requirements.txt -o requirements.lock --generate-hashes --universal --python-version 3.12
   uv pip compile requirements-dev.txt -o requirements-dev.lock --generate-hashes --universal --python-version 3.12
   (cd cloudflare && npx --yes npm@10.9.4 install --package-lock-only)
   ```

   Both compilers preserve the existing pins in the output file, so a manifest
   that did not change regenerates byte-identical output; use
   `uv pip compile --upgrade` / `npm update` deliberately for a general
   refresh and review the whole graph diff.
3. Commit the manifest and the regenerated artifacts together. The diff in the
   lock files is the dependency-graph change under review.

Dependabot files reviewable weekly update PRs for the `uv`, `npm`
(`/cloudflare`), `github-actions`, and `docker` ecosystems
(`.github/dependabot.yml`). npm and docker PRs update their pinned artifacts
directly; a Python manifest bump must regenerate the two `.lock` files in the
same PR. Merge only PRs whose locks still pass the `dependency-locks` job.

## CI gate

The `dependency-locks` job in `.github/workflows/ci.yml` runs on every push and
pull request: it installs from `requirements-dev.lock` with `--require-hashes`
and from `cloudflare/package-lock.json` with `npm ci`, then regenerates all
three artifacts with the pinned `uv`/`npm` versions and fails if
`git diff --exit-code` reports any change to tracked files. Editing a manifest
without regenerating its lock is a red build.

All third-party GitHub Actions in the workflows are pinned to 40-character
commit SHAs with a `# vX.Y.Z` comment naming the reviewed release; Dependabot
proposes SHA bumps as normal PRs.

## Rollback

To roll back a dependency update, revert the commit that changed the manifest
and lock together (for example `git revert <sha>`), or check out the previous
release's lock files. Reinstall with the deterministic commands above — the
restored lock reproduces the exact earlier graph, including integrity hashes —
then let CI re-verify before shipping.
